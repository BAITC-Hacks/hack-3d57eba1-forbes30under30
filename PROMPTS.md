# Промпты для Codex — «Аким на 5 часов»

Порядок: 1 → 2 (можно параллельно на двух машинах, разные файлы) → 3 → 4 → 5 → 6.
Codex сам коммитит и пушит по правилам из AGENTS.md. Если он написал про конфликт —
решить руками, не давать ему `--force`. Перед контрольными точками (14:00, 15:00,
16:00, 17:00, 18:00) проверить на GitHub, что последний коммит на месте.

## Промпт 1 — Каркас + данные + движок + смоук (13:15–14:00)

```
Прочитай AGENTS.md и TZ.md и следуй им. Задача: каркас проекта и детерминированный движок расчёта.

1. Инициализируй Next.js 14+ (App Router, TypeScript strict, Tailwind, без src/). Поставь openai, zod; dev: tsx. Зафиксируй версии. Добавь скрипты "smoke": "tsx scripts/smoke.ts", "typecheck": "tsc --noEmit", "engines": {"node": ">=20"}.
2. Данные уже лежат в data/districts.json и data/measures.json — не меняй их. Создай lib/engine/data.ts с типами и загрузкой этих файлов.
3. Реализуй lib/engine/validate.ts и lib/engine/score.ts строго по разделу «Движок» в AGENTS.md. Тип решения: { measureId: string; districtId?: string }. Валидатор возвращает { ok: boolean; errors: string[] } с понятными причинами на русском. score() возвращает объект с score, baseScore, delta, districts (id, name, before, after, D_before, D_after), dAvg, minDistrict, criticals, contributions по мерам, synergiesApplied. Округляй только при выводе.
4. Создай scripts/smoke.ts: загружает данные, проверяет базовый Score = 52.56, пример из ТЗ (M7@nura, M8@nura, M10@nura, M12, M5@saryarka) = 56.54 и стоимость 95, набор M9@nura, M11@nura, M10@nura, M12, M4@nura = 55.67, набор M2, M3@nura, M8@nura, M9@nura, M14 = 57.24. Также проверь, что валидатор отклоняет: 4 решения, повтор меры, бюджет 101+, M1+M3, M4+M7 в одном районе, 3 меры транспорта, городскую меру с районом, районную без района. При любом расхождении — exit code 1 с выводом ожидаемого и фактического.
5. Создай lib/openai.ts (клиент, ключ из OPENAI_API_KEY, модель из OPENAI_MODEL с дефолтом gpt-4.1-mini, понятная ошибка если ключа нет). Пока не используй его.
6. Сделай app/page.tsx заглушкой с заголовком «Аким на 5 часов» — UI придёт отдельно.

Не трогай .gitignore, .env.example, AGENTS.md, TZ.md, README.md, data/*.json. Проверь npm run typecheck, npm run build, npm run smoke. В конце коротко напиши, что создано и результаты проверок, и покажи фактические числа смоук-теста.
```

Если смоук расходится с эталоном — прислать мне числа, разберём формулу.

## Промпт 2 — UI выбора мер с бюджетом и живой валидацией (параллельно с 1)

```
Прочитай AGENTS.md. Задача: экран выбора решений. Движок делает другой человек, используй только типы и данные из lib/engine/data.ts (если файла ещё нет — создай минимальные типы и импорт JSON, потом его заменят).

1. components/MeasurePicker.tsx: каталог 14 мер, сгруппированный по 5 направлениям. У каждой меры: id, название, стоимость, лаг, эффекты (кратко: «T1 +6, T2 +9»), тип (район/город). Для районных мер — выбор района из 5. Чекбокс выбора.
2. Панель бюджета сверху: «Бюджет 100 · Использовано X · Остаток Y», прогресс-бар, красный при превышении. Счётчик «Выбрано N из 5». Счётчик по направлениям с подсветкой, если >2.
3. Живая валидация на клиенте: те же правила, что в lib/engine/validate.ts (импортируй validate, если он есть; если нет — продублируй правила из data/measures.json rules/incompatibilities и потом заменим). Ошибки показывать списком под панелью бюджета. Кнопка «Рассчитать» активна только при ok.
4. Кнопки «Загрузить пример из ТЗ» (M7@nura, M8@nura, M10@nura, M12, M5@saryarka) и «Сбросить».
5. Справа или снизу блок «Районы»: 5 карточек с названием, долей населения, профилем и текущими 10 показателями, значения < 40 подсвечены красным.
6. app/page.tsx собирает экран. Состояние в useState. По нажатию «Рассчитать» — POST /api/analyze с { decisions } (роут появится позже; пока просто console.log и заглушка результата).

Дизайн: чистый, светлый, Tailwind, без UI-библиотек. Всё на русском. Проверь npm run typecheck и npm run build. Кратко опиши, что сделано.
```

## Промпт 3 — API + агент с инструментами (14:00–15:00)

```
Прочитай AGENTS.md, разделы «Движок» и «Агентная логика». Движок и смоук-тест готовы. Задача: агент, который объясняет результат расчёта.

1. lib/agent/tools/: validate_set, score_set, get_contributions, get_district_profile. Каждый tool — zod-схема входа + функция, вызывающая движок; экспортируй описания в формате OpenAI tools.
2. lib/agent/schemas.ts: zod-схема итогового отчёта: { summary: string; strengths: string[]; risks: string[]; tradeoffs: string[]; recommendations: { change: string; expectedDelta?: number; why: string }[] }.
3. lib/agent/prompts.ts: системный промпт на русском. Роль: аналитик акимата. Жёсткие правила: никаких собственных вычислений; все числа брать только из результатов tools и цитировать их; объяснять, почему Score изменился (вклад мер, лаги, синергии, критические значения < 40, самый слабый район и его вес 30%); честно называть риски (лаг 4 квартала = эффект только 50%, район остался < 40, направление не затронуто). Ответ — строго JSON по схеме.
4. lib/agent/index.ts: runAgent(decisions) — tools loop с OpenAI (chat.completions или responses API, что стабильнее в текущем SDK): сначала агент обязан вызвать score_set и get_contributions, затем может вызвать другие tools, затем выдаёт итоговый JSON. Валидировать zod, при невалидном — один повтор с указанием ошибки. Логировать каждый шаг: { name, detail } — какой tool вызван и краткий итог. Таймаут 60 с. Ошибки — понятным текстом.
5. app/api/analyze/route.ts: POST { decisions } → validate; если !ok → 400 { errors }. Иначе → score() и runAgent() → 200 { calc, report, steps }. Если OpenAI недоступен — вернуть calc и report: null с полем aiError, чтобы UI показал числа без разбора.
6. Дополни scripts/smoke.ts: если задан OPENAI_API_KEY, один вызов runAgent на примере из ТЗ и проверка, что отчёт прошёл схему.

Проверь typecheck, build, smoke. Кратко опиши результат и покажи пример отчёта агента.
```

## Промпт 4 — Рекомендации и оптимизатор (15:00–15:40)

```
Прочитай AGENTS.md. Задача: рекомендации, подтверждённые расчётом.

1. lib/engine/optimize.ts:
   - suggestSwaps(decisions): для каждой позиции набора перебрать замену на любую другую меру и любой район (для городских — без района), оставить валидные, вернуть топ-5 по приросту Score: { replace, with, districtId, newScore, delta, cost }.
   - bestOverall(): полный перебор всех валидных наборов из 5 мер с районами. Это ≈700 тысяч вариантов — сделай перебор эффективным (предвычисли эффекты, без аллокаций в цикле, отсекай по бюджету и направлениям до назначения районов). Кэшируй результат в data/best.json; если файл есть — читать его. Верни топ-10 наборов.
2. Tool suggest_swaps для агента. Обнови промпт: рекомендации должны опираться на результаты suggest_swaps, в recommendations указывать expectedDelta из tool.
3. В API /api/analyze добавить в ответ suggestions (топ-5 замен) и bestKnownScore (из bestOverall, если посчиталось быстрее 5 с, иначе пропустить и посчитать в фоне).
4. scripts/smoke.ts: проверить, что bestOverall() находит 57.24 (M2, M3@nura, M8@nura, M9@nura, M14) или лучше, и что suggestSwaps на примере из ТЗ возвращает хотя бы одну замену с положительной дельтой.

Проверь typecheck, build, smoke, замерь время bestOverall и напиши его.
```
